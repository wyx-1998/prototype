# 重大隐患判定标准 Dify 知识库导入方案与模板

## 一、目标

本方案用于将目录 `docs/合规性检验/01重大隐患判定/00原始文档` 中的重大隐患判定标准，整理为**适合 Dify 知识库导入**的格式。

注意：

- 本文件是 **Dify 专用导入方案**。
- 不替代原《重大隐患判定标准向量知识库拆分方案》文档。
- 本方案强调的是：**怎样整理成 Dify 能吃、检索效果又尽量好的格式。**

---

## 二、先说结论：Dify 不适合直接导入“三层结构”

Dify 原生知识库更接近下面这种结构：

- 一个知识库
  - 多个文档
    - 每个文档被切分成多个 chunk
    - chunk 进入向量检索

所以，之前设计的三层结构：

- `document`
- `section`
- `rule`

更适合作为**前处理逻辑**，而不是 Dify 的直接导入结构。

如果把它原样做成三张表，Dify 本身不会按关系结构去理解。

因此，导入 Dify 时应该改成：

## 推荐的 Dify 导入映射

### 方案核心

- **每份标准 = Dify 中的一个文档**
- **每条原子判定项 = 一个 chunk**
- 原本的章节信息、条款路径、适用对象、隐患类别等，不单独建层，而是：
  - 写进 chunk 文本里
  - 或写进导入时可保留的 metadata / 备注字段中

---

## 三、最适合 Dify 的整理思路

## 1. 文档粒度

建议：

**一份标准整理为一个 Markdown 文档**。

例如：

- `城镇燃气经营安全重大隐患判定标准.md`
- `工贸企业重大事故隐患判定标准.md`
- `金属非金属矿山重大事故隐患判定标准.md`

原因：

1. Dify 的知识库通常以“文档”为管理单位。
2. 一份标准对应一个文档，最符合人工管理习惯。
3. 后续更新某个标准时，替换一份文档即可，不会影响其他标准。

---

## 2. chunk 粒度

建议：

**以“最小可判定规则”为 chunk 单位。**

也就是：

- 一条 `（一）` 如果本身就是完整规则，就切成一个 chunk
- 如果 `（一）` 下还有 `1. 2. 3.`，则以每个数字项为 chunk
- 如果是 `4.2 / 4.3` 下面还有 a)、b)、c)，则以 a)、b)、c) 为 chunk

原因：

对你的应用场景来说，用户未来问的大概率是：

- “这个情况算不算重大隐患？”
- “安全出口不足对应哪一条？”
- “未设报警装置属于什么重大隐患？”

这时候 Dify 召回的最理想单位不是一整页，也不是一整章，而是：

**一条具体判定规则。**

---

## 3. section 信息怎么处理

Dify 不适合单独导入一个 `section` 层。

因此建议：

**把 section 信息内嵌进每个 chunk 文本里。**

例如把下面这些内容放在 chunk 前部：

- 标准名称
- 标准编号
- 行业领域
- 章节路径
- 规则编号
- 适用对象
- 隐患类别
- 规则正文
- 判定结论

这样即使 Dify 只召回一个 chunk，LLM 也能拿到足够完整的语义上下文。

---

## 四、推荐的 Dify 文档组织方式

建议你最终导入 Dify 的不是原始 PDF / docx，而是**外部整理好的 Markdown 文档**。

推荐目录形态：

```text

    城镇燃气经营安全重大隐患判定标准.md

    特种设备重大事故隐患判定准则.md
    重大火灾隐患判定规则.md

```

说明：

- `00原始文档` 保留不动
- `00结构化标准库/dify_markdown/` 放清洗后的 Dify 导入文件
- 后续只把这个目录中的 Markdown 导入 Dify

## 五、推荐的 Markdown 文档结构

每个标准建议整理成一个 Markdown 文档，结构如下。

## 文档头部模板

```md

- 实施日期：待补充

适用于城镇燃气经营者重大隐患判定。

```

然后每一条规则按统一模板写入。

## 六、最关键：chunk 模板怎么写

Dify 最终是对文本切片做向量化，所以 chunk 文本本身必须带足够上下文。

推荐模板如下。

## 模板 A：最推荐的 chunk 文本模板

```md
### 规则：第五条（五）

- 标准名称：城镇燃气经营安全重大隐患判定标准
- 标准编号：无 / 待补充
- 行业领域：城镇燃气
- 文档类型：重大隐患判定标准
- 章节路径：第五条 > 燃气厂站安全管理 > （五）
- 适用对象：燃气厂站
- 隐患类别：监测报警
- 规则编号：第五条（五）
- 判定结论：判定为重大隐患

规则内容：
燃气厂站内可燃气体泄漏浓度可能达到爆炸下限20%的燃气设施区域内或建（构）筑物内，未设置固定式可燃气体浓度报警装置。
```

这个模板的优点：

1. 就算只召回这一条，LLM 也知道它属于哪个标准、哪一章、什么对象。
2. 适合直接做引用。
3. 对 Dify 的切片和召回比较友好。

---

## 模板 B：更紧凑的 chunk 文本模板

如果你担心文本太长，也可以压缩成：

```md
标准名称：城镇燃气经营安全重大隐患判定标准
行业领域：城镇燃气
章节路径：第五条 > 燃气厂站安全管理 > （五）

适用对象：燃气厂站
隐患类别：监测报警
规则内容：燃气厂站内可燃气体泄漏浓度可能达到爆炸下限20%的燃气设施区域内或建（构）筑物内，未设置固定式可燃气体浓度报警装置。

```

这个模板更适合大规模批量导入。

## 七、不同类型标准的切分方式

## 1. 条文式标准

适用文件：

- 城镇燃气
- 工贸企业
- 煤矿

建议切分规则：

- 每个 `第X条` 先作为逻辑父节点理解
- 真正写入 Dify 的 chunk，以 `（一）（二）（三）...` 为主
- 如果某个 `（一）` 下继续拆成 `1. 2. 3.`，则每个数字项单独成 chunk

### 示例

原文：

`第四条 燃气经营者在安全生产管理中，有下列情形之一的，判定为重大隐患：`

- `（一）未取得燃气经营许可证从事燃气经营活动；`
- `（二）未建立安全风险分级管控制度；`

则建议拆成两个 chunk，而不是把整条第四条合成一个大块。

原因：

未来用户搜索“燃气经营许可证”时，希望直接命中第（一）项，而不是一整条长列表。

---

## 2. 类目清单式标准

适用文件：

- 金属非金属矿山重大事故隐患判定标准
- 补充情形

建议切分规则：

- 大类目 `一、地下矿山重大事故隐患` 不单独做主 chunk
- 二级标题 `（一）安全出口存在下列情形之一的` 作为路径上下文
- 数字项 `1. 2. 3.` 作为真正 chunk

### 示例

原文层级：

- `一、金属非金属地下矿山重大事故隐患`
- `（一）安全出口存在下列情形之一的：`
- `1.矿井直达地面的独立安全出口少于2个，或者与设计不一致；`

整理后 chunk 应写成：

```md
标准名称：金属非金属矿山重大事故隐患判定标准
行业领域：金属非金属矿山
章节路径：一、金属非金属地下矿山重大事故隐患 > （一）安全出口存在下列情形之一的 > 1
规则编号：一/（一）/1
适用对象：地下矿山
隐患类别：安全出口
规则内容：矿井直达地面的独立安全出口少于2个，或者与设计不一致。
判定结论：判定为重大事故隐患。
```

原因：

如果只保留 `矿井直达地面的独立安全出口少于2个`，语义仍然不够稳，最好把“地下矿山 > 安全出口”路径一起写进去。

---

## 3. 章节式 / 国标式 PDF

适用文件：

- 重大火灾隐患判定规则
- 特种设备重大事故隐患判定准则

建议切分规则：

- 不要把封面、目录、前言、引言、引用文件作为主内容导入
- 重点整理：
  - 判定规则
  - 直接判定要素
  - 综合判定要素
  - 附录中的关键判定规则
- chunk 粒度尽量落在最小判定项上

原因：

Dify 召回的是文本语义，不是标准目录。前言、目录内容会污染召回结果。

---

## 八、哪些内容不要重点导入 Dify

以下内容不建议作为知识库主内容：

- 封面
- 目录
- 前言
- 引言
- 发布/实施说明
- 规范性引用文件清单
- 大段术语定义

这些内容如果保留，也应尽量放在文档尾部或单独区域，不要成为主要 chunk 来源。

原因：

你的目标是“判定”和“检索规则”，不是查标准编写说明。

---

## 九、推荐字段清单（面向整理，不是要求 Dify 原生支持）

虽然 Dify 最终主要吃文本，但你在前处理时仍建议维护一张结构化表，方便后续批量生成 Markdown。

推荐字段如下：

| 字段名 | 含义 | 是否建议写入 chunk |
|---|---|---|
| standard_name | 标准名称 | 是 |
| standard_code | 标准编号 | 是 |
| industry_domain | 行业领域 | 是 |
| document_type | 文档类型 | 是 |
| source_file_name | 原始文件名 | 否 |
| chapter_path | 章节路径 | 是 |
| rule_label | 规则编号 | 是 |
| applicable_object | 适用对象 | 是 |
| hazard_category | 隐患类别 | 是 |
| rule_text | 规则正文 | 是 |
| judgment_result | 判定结论 | 是 |
| publish_date | 发布日期 | 可选 |
| effective_date | 实施日期 | 可选 |
| page_span | 原文页码 | 可选 |
| confidence | 抽取置信度 | 否 |

结论：

真正影响 Dify 检索效果的，主要是这些字段被组织进 chunk 文本：

- 标准名称
- 行业领域
- 章节路径
- 规则编号
- 适用对象
- 隐患类别
- 规则正文
- 判定结论

## 十一、推荐的 Markdown 输出策略

建议用“每个标准一个 Markdown 文件”，文件中连续写多条规则。

### 示例结构

```md
# 城镇燃气经营安全重大隐患判定标准

- 标准编号：待补充
- 行业领域：城镇燃气
- 文档类型：重大隐患判定标准
- 来源文件：城镇燃气经营安全重大隐患判定标准.docx

## 判定规则

### 规则：第四条（一）
- 章节路径：第四条 > 安全生产管理 > （一）
- 适用对象：燃气经营者
- 隐患类别：许可资质
- 判定结论：判定为重大隐患

规则内容：
未取得燃气经营许可证从事燃气经营活动。

### 规则：第四条（二）
- 章节路径：第四条 > 安全生产管理 > （二）
- 适用对象：燃气经营者
- 隐患类别：安全管理制度
- 判定结论：判定为重大隐患

规则内容：
未建立安全风险分级管控制度。
```

这样导入 Dify 后，系统即使自动切片，每条规则也比较容易形成独立、完整的 chunk。

## 十二、对你这批文件的具体建议

### 1. 不建议直接把原始 docx/pdf 全量导入 Dify

原因：

- 扫描 PDF 抽取质量不稳定
- 国标 PDF 中目录、前言较多
- 直接导入后 chunk 不可控
- 后续引用定位不稳定

### 2. 建议先做外部清洗，再导入 Dify

推荐流程：

1. 原始文件抽取文本
2. 对扫描 PDF 做 OCR
3. 清除封面、目录、前言等噪音内容
4. 按最小判定规则整理成结构化表
5. 批量生成 Markdown 文档
6. 导入 Dify 知识库
7. 在 Dify 中采用较小 chunk 或自动切片验证效果

### 3. 化工 PDF 要优先确认 OCR 方案

因为从当前抽样结果看，化工这份标准很可能是图像型 PDF，后续若不先 OCR，就无法进入有效知识库。

---

## 十三、最终推荐方案

对于 Dify，最合适的格式不是三层关系结构直接导入，而是：

### 最终落地结构

- 一个标准 = 一个 Markdown 文档
- 一条最小判定规则 = 一个核心 chunk
- 条款路径、适用对象、类别、结论 = 写进 chunk 本文

可以总结为：

**“规则为中心，路径作上下文，Markdown 为载体，Dify 负责切片和召回。”**

## 十五、结论

如果目标平台是 Dify，那么最优解不是把法规做成严格的三层数据库直接导入，而是：

- 用三层思路做前处理
- 最终拍平成 Dify 友好的 Markdown 文档
- 让每一条“可判定规则”成为最核心的语义切片

这样可以同时兼顾：

- Dify 可导入性
- 检索精度
- LLM 推理所需上下文
- 标准条款溯源

如果后续要继续落地，下一步最值得做的是：

1. 为你这批标准设计统一 Excel 主表
2. 用主表批量生成 Dify Markdown
3. 先拿 1 份标准做试导入验证 chunk 效果
